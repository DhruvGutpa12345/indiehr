## Access, tenancy and security

I reviewed the access, tenancy and security lens of the backend merge 67a46185e..ddfd840db, read-only, in /home/ubuntu/indiehr-p2t0. I found no tenancy-isolation break that the tests will miss. Every new cache, lock and raw Redis key goes through the Django cache, so django_tenants make_key adds the hospital schema. The CHECK_REVOKE_TOKEN change does not matter to us, because DEFAULT_AUTHENTICATION_CLASSES is ours. I found four findings, all medium: (1) The new anonymous /metrics/ endpoint is on by default and served on every hospital host. It counts only that hospital's patients, encounters, facilities and users, and the cache key carries the schema, so it leaks nothing across hospitals. The isolation anonymous-allowlist test will catch it, but the fix is to switch it off and pin that, not to list it. (2) The new Action engine adds execute_action to bookings and runs perform_actions on create_appointment. (3) A test 'logging' instruction ships registered in production, and its authorize() always returns True. Anyone who may write a questionnaire can attach it, so patient names, phone numbers, dates of birth and questionnaire answers get written to the INFO log. That log reaches the journal, VictoriaLogs and the 400-day archive. (4) The new REPORT_ALLOWED_RESOURCE_ORIGINS / REPORT_ALLOWED_IMAGE_ORIGINS / REPORT_CONTENT_SECURITY_POLICY settings and the Prometheus settings are not pinned by secure.py. Checklist items triggered: patched files (batch_requests, valueset, users/models, patient), lock files (2 new packages, our pins untouched), new routes, permissions, spec fields, viewset swaps (CareCopies), INSTALLED_APPS (CareAdminConfig) and new settings. ### F1 (medium → downgraded low): Anonymous Prometheus /metrics/ served on every hospital host, enabled by default and not pinned

- **Upstream:** apps/backend/config/urls.py:114-115; apps/backend/config/views.py:24-28; apps/backend/config/settings/base.py:803-805; apps/backend/care/utils/metrics.py:8-17; care/emr/metrics.py:19 (Patient.objects.count()), care/users/metrics.py, care/facility/metrics.py (commit addaf5b87)
- **Ours:** plugins/ihr_platform/ihr_platform/urls_tenant.py:31 (*care_urlpatterns includes it); plugins/ihr_platform/ihr_identity/blocked.py:30-46 (not blocked); plugins/ihr_platform/ihr_platform/settings/secure.py (no pin)
- **Evidence:** ENABLE_PROMETHEUS_METRICS defaults to True and no file in plugins/ or deploy/ sets it. The view has no authentication, permission or host check. On a hospital host the search_path is that hospital's schema, so the gauges care_patients_registered, care_encounters_by_type, care_facilities and care_users are that hospital's counts. The 10-minute cache key passes through django_tenants.cache.make_key (tenancy.py:182-184), so there is no cross-hospital leak and no unprefixed key. Today it is out of the internet's reach only because frontend-nginx.conf.template:43 proxies just /api/ and Traefik routes hospitals to the frontend. Any container on the backend network can still send GET backend:9000/metrics/ with Host alpha.<suffix> and get alpha's numbers with no sign-in. Each scrape after the TTL also runs COUNT queries on patient and encounter tables. On the platform host, urls_public has no such route.
- **Failure:** The isolation suite flags '/metrics/' as an anonymous 2xx not in anonymous_allowlist.txt. A fixer then 'resolves' it by adding an allowlist row. The endpoint stays live, so a later ingress change (for example nginx proxying a new path, or a Traefik rule) or any compromised internal container publishes each hospital's patient, encounter and staff counts without authentication. The project's Prometheus has no use for it: per-hospital labels are banned by prometheus.yml's privacy rule.
- **Proposed fix:** Set settings['ENABLE_PROMETHEUS_METRICS'] = False in tenancy.apply_tenancy. Add a secure.py rule that refuses True on servers. Add rf"^metrics{END}" to BLOCKED_PREFIXES as defence in depth. Do not add an anonymous_allowlist.txt row. Log the decision in UPSTREAM_PATCHES.md or an ADR note.
- **Caught by a test:** Yes for reachability: ihr_platform.tests.isolation test_anonymous_access_matches_reviewed_allow_list fails on '/metrics/' (routes.py lists it: function view, not under SKIP_PREFIXES). No test checks the settings pin or stops it from being allowlisted.
- **Challenger:** The facts hold. This merge added the route (the pre-merge config/urls.py had no metrics route). It is registered when ENABLE_PROMETHEUS_METRICS is true, which is the default (base.py:803). plugins/ and deploy/ never set it. urls_tenant.py:31 includes it through *care_urlpatterns, and blocked.py does not block it. The view has no authentication, and the collectors count patients, encounters and users in the hospital's own schema. The isolation suite also does fail on it: test_anonymous_access_matches_reviewed_allow_list builds its open set from the crawl, and '/metrics/' is not in anonymous_allowlist.txt. But the exposure is internal only. The hospitals router in deploy/staging/traefik/routes.yml sends hospital hosts to the frontend service. frontend-nginx.conf.template proxies only /api/ (line 43) and falls back to the SPA for '/'. Traefik's own /metrics router sits on a separate entry point limited to Prometheus's IP. The suite is fail-closed, and the allow list already carries precedent FOLLOW-UP rows such as /health/*. So this is a defence-in-depth gap, not a live leak. The fix is still worth making: the settings pin, a secure.py refusal and a blocked.py prefix. One correction: 'caught_by_test' is stronger than 'reachability only'. The allow-list test forces a human review, though nothing stops that review from simply adding a row.

### F2 (medium → downgraded low): Action engine opens a write path for booking-right holders (Receptionist): execute_action and create_appointment run configured actions that change encounter priority and tags

- **Upstream:** apps/backend/care/emr/api/viewsets/action_base.py:47-68 ('# TODO: Authorize action permission' at :60; only authorize_update on the booking); care/emr/api/viewsets/scheduling/booking.py:98-102 (PERFORM_INDEPENDENT_ACTIONS = True); care/emr/api/viewsets/scheduling/availability.py:206-210, 349-361 (perform_actions + '_actions' in the response); care/action_evaluator/instruction_engine/instructions/set_encounter_priority.py:53 (encounter.save, authorize() checks only the value); care/action_evaluator/base.py:119-131 ('{{field}}' params evaluated from patient context fields)
- **Ours:** plugins/ihr_platform/ihr_roles/registry.py:141-150 (Receptionist holds can_write_booking); plugins/ihr_platform/ihr_access/views.py:715 (IhrSlotViewSet inherits SlotViewSet unchanged for create_appointment); TokenBookingViewSet is not swapped (route_swaps.SWAPS)
- **Evidence:** execute_action authorizes only booking update (authorize_update), then evaluates the stored instructions as request.user. set_encounter_priority writes Encounter.priority, and tag_patient/tag_encounter apply tags. The tag check happens only when the action is authored, against the author. Our ihr_access encounter swap limits what restricted users may write to an encounter, but these writes never go through the encounter viewset or our guard. Instruction outputs are returned raw in '_actions' (TokenBooking create) or as the response. They can interpolate patient context fields (blood group, DOB, phone, deceased) that are not serialized through the guarded specs. Today only a superuser can create Action rows (action.py:49,61), so the gap is latent.
- **Failure:** An operator or superuser creates a performable APPOINTMENT action (for example 'set priority urgent and tag patient'). Receptionist reception.ravi POSTs /api/v1/facility/<f>/token/booking/<id>/execute_action/ {action:<uuid>}, or simply books a slot. The visit's priority changes and the patient is tagged under the receptionist's name, through no route ihr_access reviewed. A 'logging' or show-style output with '{{patient_blood_group}}' returns a field that the projection hides from the front desk. The role matrix sees only a 400/404 'body' answer because its world has no Action rows, so it passes.
- **Proposed fix:** In ihr_access, close the action engine for branches.restricted users: a booking/slot swap that raises PermissionDenied on execute_action and strips '_actions' from responses (or skips perform_actions) for restricted users. Add a check that fails if a new class mixes in EMRActionBaseViewSet unreviewed. Alternatively set ACTIONS_ENABLED off and refuse action_configuration writes on hospital hosts until an owner decision (QUESTIONS.md). Add a role-matrix world row with one performable Action so the matrix exercises it.
- **Caught by a test:** No: test_role_matrix records execute_action as a new write route, but with no Action row in the world it never shows the write or the unprojected output.
- **Challenger:** Mostly latent, and two of the three claimed effects are wrong. (1) The priority write does not happen on the booking and slot paths. execute_action and create_appointment evaluate with context 'Appointment', and TokenBooking has no 'encounter' attribute, only associated_encounter (models/scheduling/booking.py:39). resolve_encounter (instruction_engine/resolvers.py) does getattr(obj,'encounter') and so returns None, which gives 'not attached to an encounter' and no save. A priority write is reachable only through encounter or questionnaire contexts, which depend on the submitter's existing encounter rights. (2) The claim that 'the tag check happens only when the action is authored' is false. The tag managers re-check at apply time against the acting user: tagging/base.py:99 calls AuthorizationController.call('can_apply_tag_config', user, tag), and tag_resource.py catches PermissionDenied. Our authz layer can then deny a Receptionist. (3) Creating Action rows needs a superuser (action.py:49 and :61), and facility-level creation is refused outright. Hospital staff are non-superusers by design: the directory excludes superusers, and views.py:267 and join.py:215 create users with is_superuser=False. What stays real is the 'TODO: Authorize action permission' gap in execute_action, with only authorize_update on the booking, and the raw instruction outputs returned in '_actions'. That matters only if a performable APPOINTMENT action exists. The reviewer's 'caught_by_test: No' is also too weak: role_matrix.txt has no row for execute_action or action_configuration, so the matrix should flag the new routes as unreviewed. It does not exercise the output because the world has no Action rows. A reviewed deny, or a world row, is a sensible follow-up, and so is a refusal to create Action rows on hospital hosts.

### F3 (medium → confirmed ): Test 'logging' instruction ships registered and is authorizable by any questionnaire author, so patient data and answers reach the INFO log

- **Upstream:** apps/backend/care/action_evaluator/instruction_engine/instructions/__init__.py:1 (from .logging_test import *); logging_test.py:25 (logging.info(f"Logging Action Instruction: {self.inputs}")), :30 (authorize returns True); care/action_evaluator/context_engine/fields/patient.py:15-19 (TestContext1 'test1234' also registered); questionnaire actions evaluated on submit at care/emr/api/viewsets/questionnaire/questionnaire.py:455-472, authorized only through ActionEvaluator.authorize (:232-235)
- **Ours:** apps/backend/config/settings/base.py:392 (root logger INFO to console) -> journald -> Fluent Bit (deploy/logs/fluent-bit/redact.lua redacts Aadhaar/ABHA-like numbers and user names in paths, not patient names or free-text answers) -> VictoriaLogs 180 days and the 400-day archive (ADR-014)
- **Evidence:** ActionEvaluator.evaluate_instruction does not enforce the instruction class's declared context. Params of the form '{{q_<answer>}}' or patient fields (name, phone, DOB) are evaluated from the field cache. The 'logging' instruction then writes them verbatim with logging.info. A facility- or user-level questionnaire can be authored by staff who hold questionnaire write rights, not only superusers. ActionEvaluator.authorize only checks that the instruction exists and that its authorize() returns True, and for 'logging' it always does.
- **Failure:** A hospital admin builds a triage form with the action {condition:'True', instructions:[{slug:'logging', context:'self', params:{message:'{{q_complaint}} {{patient_name}} {{patient_phone_number}}'}}]}. Every submission writes clinical free text and identifiers into the application log. That log is kept 180 days in VictoriaLogs and 400 days encrypted in the archive, and can be erased only by the owner (CERT-In vs DPDP minimisation).
- **Proposed fix:** At start-up (for example ihr_access or ihr_platform AppConfig.ready), unregister the 'logging' instruction and the TestContext1 dynamic field from ActionInstructionRegistry/ActionFieldRegistry. Add a system check that refuses any registered instruction whose slug is not on a reviewed list. Alternatively remove the import as an apps/ patch logged in UPSTREAM_PATCHES.md. Add a deploy/logs/tests redaction case, and consider reporting it upstream.
- **Caught by a test:** No
- **Challenger:** The registration and the log line are as stated. instructions/__init__.py:1 imports logging_test, which registers slug 'logging' with authorize() returning True. Its evaluate() runs logging.info(f'... {self.inputs}'), and the root logger is INFO to console (base.py:392). TestContext1 is registered too. ActionEvaluator.authorize (base.py:63-76) checks only that the instruction exists and that its authorize() passes. It does not enforce the instruction's declared context, so a questionnaire action can name 'logging'. The questionnaire handler (questionnaire.py:232, 235, 281) calls this check at authoring time. At run time, evaluate_instruction fills params from patient fields (name, phone_number, date_of_birth, blood_group, and others) and from q_ answers, and the output goes to the log. No plugin unregisters it. One correction to the failure scenario: placeholder substitution only fires when the WHOLE param string starts with '{{' and ends with '}}' (base.py:118-122). The multi-placeholder message in the example would be evaluated as one malformed expression. One field per param works, for example {a:'{{q_complaint}}', b:'{{patient_name}}'}, and the free-form inputs dict is not schema-checked. The severity stays medium for log retention (180 days in VictoriaLogs, 400-day archive, owner-only erase) of patient identifiers and clinical text. The author must be a trusted hospital questionnaire writer, which tempers likelihood. Unregistering the instruction and the test field at AppConfig.ready, plus a reviewed-slug system check, is cheap and right.

### F4 (medium → downgraded low): New report-rendering origin and CSP settings (server-side outbound fetch) are not pinned by secure.py

- **Upstream:** apps/backend/config/settings/base.py:735-752 (REPORT_ALLOWED_RESOURCE_ORIGINS, legacy REPORT_ALLOWED_IMAGE_ORIGINS fallback, REPORT_CONTENT_SECURITY_POLICY override); care/emr/reports/renderer/generators/weasyprint_generator.py:92-99 (fetches allowed https origins at render time); care/emr/reports/renderer/resource_policy.py:44-53 (commits e53ea4375/ba8c4f208)
- **Ours:** plugins/ihr_platform/ihr_platform/settings/secure.py:190-197 (pins only FACILITY_CDN unset, which keeps the default list empty)
- **Evidence:** With FACILITY_CDN refused, the default origin list is empty, so today no report fetches anything remotely. But either env var can be set in a server's .env without any secure.py refusal. WeasyPrint would then make outbound HTTPS requests from the backend during PDF rendering, which is a new run-time egress that the bundle-egress and CSP reviews never see. A REPORT_CONTENT_SECURITY_POLICY override can loosen the CSP sent with saved and served HTML reports.
- **Failure:** An operator follows upstream's .env.example and sets REPORT_ALLOWED_RESOURCE_ORIGINS=https://some-cdn.example for a hospital logo. Every PDF report now fetches from a third-party host outside India and outside reviewed egress, and the deployment still starts cleanly.
- **Proposed fix:** In secure.problems, refuse non-empty REPORT_ALLOWED_RESOURCE_ORIGINS and REPORT_ALLOWED_IMAGE_ORIGINS unless every origin is on a reviewed list (for example the files.<suffix> host, if signed picture links are ever wanted in reports). Refuse a custom REPORT_CONTENT_SECURITY_POLICY. In the same pass, pin ENABLE_PROMETHEUS_METRICS False (F1).
- **Caught by a test:** No
- **Challenger:** The facts hold, but only a trusted operator's .env can trigger it. base.py:735-752 shows REPORT_ALLOWED_RESOURCE_ORIGINS defaulting to [FACILITY_CDN] or empty. weasyprint_generator.fetch() allows a remote fetch only when is_allowed_remote_resource passes. secure.py:190-197 refuses FACILITY_CDN and does not pin the two REPORT_* origin settings or REPORT_CONTENT_SECURITY_POLICY. So today there is no egress and the CSP default is closed. There is no user-controlled path to set these, and the risk is a configuration mistake, not an attack. This is a straightforward hardening item that belongs in secure.problems next to the FACILITY_CDN rule. Pin ENABLE_PROMETHEUS_METRICS in the same pass (F1).
