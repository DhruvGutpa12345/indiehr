# P1-T19a independent code review (2026-11-13)

Two fresh Opus reviewers who did not write the code (security; correctness), then a third agent
tried to refute each finding. Of 18 findings in the review file (10 security S1-S10, 8 correctness
C1-C8): 3 refuted (S7, S9, C7), 9 confirmed in part and 6 confirmed. A fixer agent fixed the 15
that stood, an independent verifier checked each fix against its failure scenario and found two
regressions and several gaps, and a second fixer closed them. Mutation proof: each of the 19 fixes
was mutated one at a time (the controls the first round never mutated included), and every
mutation was caught by a test; the files were restored byte for byte. Final runs, all green:
app-role mode (`IHR_DB_ROLES=test`, all eight labels) Ran 589 OK (skipped=45); off mode Ran 557 OK
(skipped=48); `scripts/check-logs.py` OK; `scripts/isolation-mutation.sh check` 42 targets found;
`pre-commit run --all-files` OK. Nothing committed.

## Fix regressions found by the verifier

The independent verifier closed S1, S4, S5, S6, C1, C2, C3, C5 and S10, and marked S2, S3, S8, C4, C6 and C8 partly. It also found new problems in the first fixer's work, all handled by the second fixer:

- **S3 default revoke broke `ihr_audit_last4` (high, latent until `IHR_DB_ROLES=required`).** The `ALTER DEFAULT PRIVILEGES ... REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC` stopped PUBLIC executing every function the owner creates afterwards, including each new hospital schema's `ihr_audit_last4`. The audit row trigger runs as `ihr_app` and calls it directly, so every write to a masked identifier column in a hospital created after the move would have failed with "permission denied for function". Test mode could not see it (the owner is the superuser there). Fixed: `ihr_audit_last4` is in `db_roles.FUNCTIONS` with EXECUTE for `ihr_app` only, any other non-trigger function outside the model is a problem, and a test creates the helper under the default revoke and writes a masked column as `ihr_app`.
- **C2 gating weakened fail-closed.** Before, an extra right in any hospital schema refused every process; now the shared `ihr_app` role keeps the right while other hospitals are served, so an injection through a served hospital could use it in the gated one. Mitigated, not removed: a fleet-wide `ihr_fleet_run migrate` now converges every schema in the catalogue (archived, deferred, no hospital row), a fleet-wide `check` reports them, the new alert `DatabaseSchemaGated` names each gated schema every minute (archived included), and anything that is a way to the owner's rights (CREATE on any schema, a definer function the app may execute) still refuses the process. Residual recorded as Known limit 5.
- **Controls counted only at run time.** The queue guard and the sealing functions were reported as one warning count. Now a control problem in public or the database refuses the process (`controls`), and in a hospital schema gates that hospital.
- **Refusals as levers (S2, S8).** `ALTER ROLE ihr_app SET ...` or a leftover large object can make every app container refuse. Accepted (availability against a compromised app role is not a goal) and written into the P1-T19b runbook in `deploy/staging/README.md`.
- **C6 stale deferred error** in a later migrate of the same process: fixed with the `pre_migrate` clearing receiver.
- **C8 gaps** (`session_authorization` spellings, `DISCARD ALL`): closed in the test wrapper.
- **Process note:** the first fixer's mutation proof applied 16 mutations at once; the second round redid it one at a time, 19 of 19 caught.
