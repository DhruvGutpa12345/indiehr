# P1-T9d design: Grafana dashboards and access (draft, then the attack's changes; built as ADR-015)

## Goal

The operator (one person, the owner) sees the stack's health at a glance and can search the
redacted logs, from their own machine. This needs nothing published on the server and no new way
in.

## Components

1. **Image `indiehr-grafana:staging`** (`deploy/docker/grafana.Dockerfile`).
   - **Base:** `grafana/grafana:13.3.1@sha256:0615ec4f…` (OSS, AGPL-3.0, unmodified).
   - **Plugin:** a build stage fetches the VictoriaLogs datasource v0.34.0 zip with
     `ADD --checksum=sha256:6fc61446…` and unzips it into `/opt/ihr-grafana-plugins`
     (`GF_PATHS_PLUGINS`, outside the data volume). Nothing is downloaded at run time.
   - **No outside calls** (image ENV):
     - analytics reporting, update and plugin-update checks, feedback links, news;
     - gravatar, external snapshots, plugin preinstall and auto-update;
     - the plugin admin UI;
     - Grafana-managed alerting (Prometheus, Alertmanager and vmalert stay the only alerting).
   - **Built:** by `scripts/deploy.sh`, and by a CI job "Grafana image" that builds it,
     smoke-tests it (health, the plugin registered, no outside calls attempted with
     `--network none`) and Trivy-scans it.
2. **Service `grafana`** (`deploy/staging/compose.dashboards.yaml`, on with monitoring).
   - **Hardening:** read-only root, no capabilities, no-new-privileges, `mem_limit 768m`.
   - **User:** the owner of `secrets/` (it reads its secrets from there, mode 600).
   - **Storage:** data volume `grafanadata` (SQLite) owned by that user via a one-off
     (`grafana-data`, the alertmanager-data pattern); tmpfs `/tmp`.
   - **Secrets:**
     - `secrets/grafana-admin-password`: the admin account, set on first start only (rotate:
       `grafana-reset-admin`);
     - `secrets/grafana-secret-key`: encrypts datasource secrets in its database;
     - `secrets/logs-http-password`: the log store.
   - **Networks:** `monitoring`, with a fixed address `IHR_GRAFANA_IP` 10.203.0.71 (the tunnel
     target), to reach Prometheus; and `logs`, to reach VictoriaLogs. It is **not on
     `alerting`**: Alertmanager's API has no login, and the dashboards show `ALERTS` from
     Prometheus instead. It is on no network with a way out.
3. **Access.**
   - The SSH tunnel only: `scripts/staging.sh ops-tunnel` adds `-L 127.0.0.1:3000:<grafana>:3000`.
   - **Sign-in:** Grafana's own login, one admin account, no anonymous, no sign-up,
     brute-force protection on (Grafana's default).
   - **Cookies:** `GF_SERVER_ROOT_URL=http://127.0.0.1:3000/`; cookie not secure (plain http on
     loopback), SameSite lax.
   - **A proof on this machine** publishes 127.0.0.1:3000 itself
     (`compose.dashboards.local.yaml`), for the owner's click-through.
4. **Datasources** (provisioned, not editable): Prometheus (`http://prometheus:9090`) and
   VictoriaLogs (`http://victorialogs:9428`, basic auth `ihr-logs`, password from the file).
5. **Dashboards** (provisioned read-only from `deploy/grafana/dashboards/*.json`, folder
   "IndieHR"; UI edits are not saved, changes go through git). They are generated by
   `deploy/grafana/build_dashboards.py` (stdlib) from compact definitions; a test checks the
   committed JSON is what the script makes.
   1. **Server and stack:**
      - host CPU, memory, swap, disk, NTP offset;
      - containers running, unhealthy and restarts; memory working set against each limit;
      - targets up; firing alerts (`ALERTS`).
   2. **Data and records:**
      - Postgres: up, connections per database, longest transaction, WAL archiving;
      - Redis: memory, persistence, Celery queue;
      - backups: age of the last good one, WAL spool;
      - log store: ingest rate, disk against its cap;
      - archive: the newest day, failing passes, not authentic, bucket lock;
      - journal: size against its cap, oldest entry age;
      - client-key ages and certificate expiry.
   3. **Traffic and sign-in:**
      - Traefik requests per router and status, 429s, p95 latency;
      - public probes and their latency;
      - from the logs: sign-in failures and lock-outs over time, and the addresses with most
        failures (a table).
   4. **Logs:** a log panel with service and source filters; lines per service; error-level
      lines per service.
6. **Checks.**
   - **Static** (`scripts/test_staging_dashboards.py`):
     - the hardening and the image ENV;
     - networks: on `monitoring` and `logs`, never `alerting`, `edge` or `internal`;
     - nothing published except in the local overlay;
     - the admin password and secret key from files;
     - the dashboards are current with the generator;
     - every panel names a provisioned datasource;
     - no panel query groups by a personal field (`client_ip` only in the sign-in table, by the
       owner's Q-O8).
   - **Live** (`smoke`):
     - Grafana healthy;
     - signing in with the admin password works, and a wrong password is refused;
     - both datasources answer through Grafana's own health check;
     - every panel's query runs without error against Prometheus and VictoriaLogs;
     - nothing published on a server;
     - the web app cannot reach Grafana.

## Decisions (auto-accepted, awaiting the owner)

- **Q-O13** Dashboards: Grafana OSS (as in PLAN), unmodified, VictoriaLogs plugin baked in by
  checksum, viewer-only (no Grafana alerting), dashboards from git, read-only. Runner-up Perses.
- **Q-O14** Access: SSH tunnel only, Grafana's own admin login, no single sign-on yet. SSO
  through the operator realm (Keycloak, MFA) is an option later.

## After the design attack (2026-11-12): 17 findings confirmed, 1 rejected

Two reviewers attacked the draft above: security and feasibility. Each finding was challenged,
and 17 survived. The built design is ADR-015. This table shows how each finding changed it.

| # | Finding | Resolution |
|---|---|---|
| 1, 9 | On `monitoring`, the internet-facing containers could reach Grafana, so the planned "web app cannot reach it" check would fail | Grafana moved to a new internal network `dashboards` (.48/28) with Prometheus and logs-reader only. It has a fixed .50 address and listens on that address alone. Static and live checks added |
| 2 | Anyone who reaches Grafana can lock out the default `admin` name | The name and e-mail are generated (`ops-<hex>`). Recovery is `grafana-reset-admin`; a lock-out lasts 5 minutes |
| 3, 16 | Trivy found 20 HIGH in bundled plugins and the logs plugin | Unused bundled plugins removed and disabled. What remains (Prometheus, the plugin) is path-scoped with an expiry; the findings are unreachable here. Removing the plugin's other-platform binaries breaks its signature, so they stay |
| 4 | DNS rebinding | `enforce_domain` with the single name `grafana.localhost`; `/metrics` off. Smoke checks that a foreign Host is redirected |
| 5 | Grafana held the log store's single password, so it could write to the record | vmauth `logs-reader` with a read-only `grafana-ro` login: `/select/logsql/` only. Tested: insert, flush, vmui and path tricks get 400 |
| 6 | No CSP, long sessions | A strict CSP template in the image; 12 h maximum, 1 h idle |
| 7 | Every 127.0.0.1 tunnel page counts as same-site | The `grafana.localhost` host name gives Grafana its own site and cookie. Smoke checks that a cross-origin write is refused |
| 8 | Rotating the password file does nothing, and a reset could leak it | `grafana-reset-admin` passes the password on stdin and updates the file only on success. Secrets are made once and refused if the volume exists without them. A static test requires `--password-from-stdin` |
| 10 | The local overlay cannot publish ports from an internal-only container | No overlay. The proof reaches the fixed address directly, with `IHR_GRAFANA_DOMAIN` (allowed only with `.local`) |
| 11 | The firing-alerts panel missed the log alerts | It now has two queries (`ALERTS` + `vmalert_alerts_firing`) and a "log alert rules running" stat whose threshold comes from the rule files |
| 12 | Provisioning changes did not reach a running Grafana | grafana and logs-reader added to `monitoring_settings` and the restamp list. Folders are mounted, not single files |
| 13 | deploy.sh did not send deploy/grafana | It now sends it, binds use `create_host_path: false`, and a static test checks that every bind source is shipped. The image is labelled with the Dockerfile's hash |
| 14 | "The query runs" passes on empty panels | Static: every metric must be emitted by a known exporter or our scripts, and every log field must come from the pipeline. Live: every query must return data unless it is listed with a reason |
| 15 | 768 MB was 3× the need | The limit is now 512 MB (measured 270 MB) and can be changed with `IHR_GRAFANA_MEMORY`. A memory note is in the README |
| 17 | `--network none` cannot show that no call was attempted | CI runs the image on an internal network, greps the log for lookups or dials after 60 s, and checks `/api/admin/settings` value by value |

**Rejected:** "this does not fit in 3–4 h". The estimate was the run file's, not part of the
design, and the reviewer showed no flaw. The task did grow, and the run file records the
measured time.
