# Query and path parameters for the role matrix (P1-T11b3; design-b.md "After the attack" §10
# item 12). The isolation crawl fills path parameters only (routes.fill()), so CARE's lists that
# need a facility, a patient, an encounter or a place would answer every role alike (400 or
# empty) and the branches behind them would go untested.
#
# One line per extra request of a route: <route> ?<name>=<world object>[&...]  # why
#   name=obj        a query parameter: that object's id (ihr_access.testing world.objects)
#   name=obj.attr   a query parameter: that attribute of the object
#   name~text       a query parameter with a literal value
#   {param}=obj     the path parameter takes that object's id instead of its model's default
# The route with no parameters is always requested as well. Its key in role_matrix.txt is the
# route plus the assignments, exactly as written here.
# <route> none[:key1,key2]  # why: a route whose view reads the query string but needs no extra
# request here; ``none:`` names each optional key reviewed (a bare ``none`` names none). Every
# query key the crawl sees CARE's or our code read on a route (POST reads included, as
# ``POST <route>``: their keys also come from post_reads.txt assignments) must be named by a
# variant or a ``none:`` key of that route (RoleMatrix.test_every_query_read_has_a_params_line;
# review NEW-2: a new key CARE starts to read fails until reviewed). A line is also required for
# every route whose view class reads the query anywhere in its own or inherited code (ListParams,
# a static walk of the MRO), detail routes and actions included. Every route under a patient is
# also requested with ?encounter=encounter_b (matrix.CROSS, generated: another patient's visit,
# review K1/K2); that covers its "encounter" key, and only that one: any other key its classes
# read by name must be named by a line (ListParams, review NEW-1).
