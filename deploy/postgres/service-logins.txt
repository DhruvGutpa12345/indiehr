# The reviewed service logins (P1-T27a, design.md §4.4): the database sessions that are not an
# operator's and so carry no "op:<session>:" application name. One per line, tab-separated:
#   <container's compose service or name>	<role>	<application name, exact; - for none>	<who, why>
# The log alert PrivilegedLoginUnrecorded (deploy/logs/alerts/operator.yml) leaves out exactly these
# (service, role, application) triples; scripts/test_staging_operator.py checks the two agree.
# Any other session that Postgres authorizes, and an op:<session> name whose session is not open,
# alerts. The application name is chosen by the client: a deliberate insider can borrow one of
# these (ADR-010, P1-T27 amendment); the alert catches mistakes and the careless path.
# Built from the code (2026-11-22). The local proof (design.md §9.4 step 4) captures every
# "connection authorized" line of a full local-proof, release and hospital-restore-drill run and
# corrects this list; until then a missing line shows as a false alert, never as a silent one.
# Corrected by the live proof (docs/reviews/p1-t27/live-proof.md, F1-F4, PG 18.6): Postgres logs
# this line at login, before a client's own SET application_name, so pgBackRest (2.60: libpq, no
# name at login) and Keycloak (pgjdbc: SET after login unless assumeMinServerVersion >= 9.0) showed
# no name; both are now named at login. Never list an empty name, psql or pg_isready for postgres:
# an operator's careless raw session looks exactly like that. The postgres image's init scripts on
# a new data directory (two psql lines) alert once; deploy/staging/README.md says how to tell them.
